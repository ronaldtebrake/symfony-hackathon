# After the hackathon

Our goal is for a Symfony developer to publish a team procedure using services the application already has. Today the bundle can expose approved readers through an authenticated MCP catalog. The refund demo adds Group discovery, instructions and two ways to reach the same readers. These are the decisions and experiments still ahead. [Reusable catalog](../../packages/symfony-code-mode/src/Http/CatalogTools.php) · [Refund Group implementation](../../src/Demo/GroupSelection/Discovery.php)

## Decide what belongs upstream

An agent using Symfony AI can search its toolbox and call a tool it discovers. Our application serves a different caller: an external MCP client. It advertises two stable tools, one to find definitions and one to execute approved operations. An opt-in Symfony MCP bundle integration could supply that adapter. Applications would supply the tools, team instructions and access rules. Whether the catalog needs a generic execution tool is an open design question.

## Try a second Symfony app

- [ ] **Check dependency compatibility.** Our package currently requires PHP MCP SDK `^0.9`. Try the newer SDK and matching Symfony MCP bundle in a clean app, including an authenticated HTTP session, before changing that constraint. [Package requirements](../../packages/symfony-code-mode/composer.json) · [Symfony’s SDK 0.10 integration](https://github.com/symfony/ai/pull/2906)
- [ ] **Publish one procedure outside the refund demo.** Use the upstream decisions above to choose the smallest implementation. In a fresh app, register a slow-route investigation with its own instructions and approved profiler and log readers. Connect an ordinary MCP client, follow the returned request identifier into the next read, and verify that the app enforces the caller’s access. Record what still requires custom code and what we can retire.
