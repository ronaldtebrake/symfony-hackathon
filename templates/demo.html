Find the Symfony tools a job needs.

A growing Symfony app can offer an agent dozens of tools. Sending every definition up front costs tokens, and a long list still tells the agent little about how a team uses those tools together. Symfony Code Mode gives the agent a searchable catalog over the Model Context Protocol (MCP) so it can discover approved tools as it needs them.

Why we moved from sandboxed PHP to a catalog

Sandboxed PHP let the agent combine tool results and send only the rows it needed back to the model. Hosting that sandbox was the hard part. For operations the app already supports, we could send a tool name and JSON arguments to an installed Symfony service. The PHP MCP SDK made that possible over ordinary HTTP.

MCP over HTTP · Symfony prototype

From a user’s question to a Symfony tool

The user asks a question in the agent app. The model proposes a tool and its arguments. The host sends that call over MCP, gives the result back to the model, and returns its answer to the user. Symfony checks the actual read each time.

What did this project add?

Symfony AI runs the conversation. Its MCP bridge gives the model tools from the remote server. On the server, Symfony’s MCP bundle and the PHP SDK expose the application services. We added the catalog. It publishes two entry tools, searches the approved definitions visible to this user, and checks the actual operation, arguments and remaining budget inside each execution.

For example, permission to call execute_tools alone cannot decide whether the user may read a particular record. Our integration obtains that decision from the application before invoking the reader. The separate Groups prototype lets a compatible client open a named set of tools and use the same checks on each read. Compare our work with the released components and proposals →

The design journey

From running an agent’s PHP to sharing the tools and the guide.

Our first question was how an agent could use one tool’s result in its next call. Once we could run the calls, we wanted to know how the agent would find the tools that belong together.

Our first Code Mode server let an agent write PHP to page through articles and match them to images. Ask what it takes to host that program.

Generated PHP ran in a fresh gVisor sandbox. A broker held the credentials and checked each read. This worked, including the timeout test, but adopting it meant operating a Linux sandbox alongside the Symfony app. The tool handlers were already trusted PHP services. Calling one of those services did not need a second runtime.

Ordinary Symfony hosting, explicit boundaries

The JSON catalog runs inside your application. It needs PHP, Composer dependencies and writable host state; there is no worker option, process-control extension, Docker daemon or generated-code runtime on this path.

Symfony Security authenticates each HTTP request. Application policy checks every tool call. Discovery and execution budgets are stored per authenticated user, with a lock and reservations saved before handlers run. Reconnecting or restarting the server does not reset them; the operator resets a budget explicitly.

Call counts, schemas and result sizes are checked by the package. Time checks are cooperative: a blocked handler cannot be interrupted in-process. Configure request termination, database timeouts and HTTP-client timeouts in your hosting and application. A client timeout alone does not stop server work.

The default state store supports one application host with persistent storage. Multiple replicas need a shared state store and lock; the local proof does not certify every hosting provider. Executing generated PHP requires the separate gVisor runner.

01

Connect your agent

Generate a local bearer token:

php -r 'echo bin2hex(random_bytes(32)), PHP_EOL;'

Save it in examples/symfony/.env.local, which Git ignores. Preserve any other settings:

ADOPTION_MCP_TOKEN=<the generated value>

Prepare a new take, then leave this server running:

php examples/symfony/bin/console demo:reader-access grant
php examples/symfony/bin/console code-mode:reset-budget demo-reader
composer start --working-dir=examples/symfony

Configure your MCP client with the same token:

URL: http://127.0.0.1:8001/mcp
Authorization: Bearer <the same value>

Bring the same integration to your own tools

Register approved Symfony AI services and share your application voter between discovery, calls and controllers:

code_mode:
    mode: catalog
    ai_tool_services: [Adoption\ArticleTool]
    ai_tools: ['publication_read']
    voter_rules:
        publication_read:
            discover: PUBLICATION_DISCOVER
            execute: PUBLICATION_READ
            subject: id
    http:
        enabled: true
        permissions:
            publication.read_published: ROLE_READER

    The trust boundary
    Useful access.
    Explicit limits.
    The host owns identity, tool permissions and budgets in both paths. JSON avoids running generated programs; it still invokes application code.
    01 / BOTH PATHSAuthorize every call
    Approved providers, schema validation and application access checks. Search results and tool descriptions never grant permissions.
    02 / JSONLiteral calls only
    No PHP, expressions, loops or result references. Existing handlers run in the application process. Calls stop on first failure; completed calls are not rolled back.
    03 / SANDBOXED PHPgVisor is required
    No unsafe local executor or ordinary-container fallback. The guest has no network, host mounts, credentials or Docker socket.
    04 / BOTH PATHSBounded work
    Host-owned call and output budgets. JSON deadlines are cooperative; hosting controls hard time and memory limits. The sandbox enforces separate time and memory limits for generated code.
    Authorization limits access; it cannot establish user intent for every otherwise permitted action. The live injection test demonstrates that distinction. These development proofs are not an independent security audit or a production-hosting certification.
