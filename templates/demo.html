A dedicated Linux runtime, gVisor and a pinned runner image are infrastructure an ordinary hosted Symfony app cannot provision through Composer. The smaller performance investigation also used more tokens than direct calls: discovery and code generation have a cost.

Version two · simpler adoption

From PHP to JSON.

The agent discovers an approved tool and sends JSON arguments. Your Symfony application runs its existing handler and returns the result.

What runs now?

In mode: catalog, the PHP MCP SDK serves two entry tools: search_tools and execute_tools. Symfony AI provides the application tool contracts and invokes the installed PHP services. The agent supplies data; it supplies no PHP program. This path does not start Docker or gVisor.

  1. 01 / DISCOVERFind the contract

    search_tools returns approved names and full JSON schemas. Search does not grant access.

  2. 02 / CHECKValidate each call

    execute_tools accepts literal arguments. The broker checks discovery, host identity, policy and schema.

  3. 03 / RUNCall your service

    A supervised PHP CLI child invokes the trusted handler through Symfony AI. The agent receives its result.

A working Symfony application

Read an article through its existing tool.

The separate Composer example owns its articles, Symfony AI toolbox and publication policy. It exposes publication_read; another annotated tool, publication_count, remains outside the approved catalog. These are synthetic records in a real Symfony CLI application.

The agent sends JSON.

// search_tools
{"query": "publication"}

// execute_tools, after discovery
{"calls": [{
  "name": "publication_read",
  "arguments": {"id": 101}
}]}

One call is enough. Multiple independent calls may share a submission; calls needing earlier results wait for another submission.

Symfony runs installed PHP.

// ArticleTool::read — the registered Symfony AI handler
public function read(int $id): array
{
    return $this->articles->readPublished($id);
}

// ReadPolicy::isGranted — checked before invocation
return $identity->allows('publication.read_published')
    && 'publication_read' === $tool
    && ['id'] === array_keys(get_object_vars($arguments))
    && is_int($arguments->id)
    && $this->articles->isPublished($arguments->id);

Source excerpts: tool service · application policy. The data service also checks publication before returning a record.

The permitted read returns article 101 and its title. Reading 202 returns tool_denied, without invoking the article handler. Inspect the native MCP rehearsal →

The worker, the sandbox, and hosted Symfony

The catalog still uses a separate PHP CLI process to supervise trusted handlers: deadlines, call and output budgets, and process cleanup. It uses pcntl and posix on Unix. This worker has host capabilities; it is not a sandbox for hostile PHP. Only installed, approved handlers may run.

The optional mode: php path accepts generated PHP and therefore requires the separate gVisor runtime. The catalog never constructs that sandbox. Both paths use the same provider contracts and broker checks.

A Symfony deployment can run the JSON server as a CLI service where those extensions and child processes are available. Shared hosting that only permits web requests is not yet supported by this worker. A portable worker adapter remains future work. The example’s fixed local identity is not remote authentication.

JSON removes arbitrary program execution, but tool output can still contain prompt injection. The application must enforce access on every call, regardless of what the agent asks.

How we arrived here

Running generated code meant operating a separate environment for it. Our gVisor setup enforced the boundaries we tested, but it also needed a dedicated Linux runtime and a pinned runner image. Installing a Composer package could not take care of that infrastructure.

The content-query experiment made another option clearer. The application could run the query itself, check access and return a defined result. Its inputs and outputs already had JSON Schema contracts exposed through MCP. For that kind of task, the agent could supply the arguments directly.

While exploring that route, we found Pushpak Chhajed’s story of building MCP servers with Laravel. His move from generated PHP to a searchable JSON catalog helped clarify our own direction: keep discovery and the application’s existing handlers, and make generated-code execution optional.

The same checks in both pathsApproved providersHost-owned identityArgument validationAuthorization per callExecution budgets

JSON removes the generated program, not the need to trust and supervise tool handlers. There are no expressions, loops or result-reference language to interpret. Calls stop on the first failure; completed calls are not rolled back.

Simpler deployment is a reason to choose JSON. Token savings need evidence.

The three-way audit keeps the model, question, data and permissions fixed. It records failed attempts and includes the shared answer-review cost. Fewer dependencies can justify JSON even when computation in PHP uses fewer tokens.

What we learned from the article

Credit to Pushpak Chhajed for documenting the trade-offs and the fixed search/execute interface. We reuse Symfony AI schemas and our own broker, disclosure checks and supervised handlers. Read his reflections on testing the design.

The article’s flat catalog measurement covers advertised tools/list bytes. Search results and later conversation work still cost tokens. Our measurement separates those two costs.

JSON also does not prevent prompt injection. Laravel’s catalog dispatcher rechecks tool eligibility; resource authorization belongs in the application. Our own injection test shows why allowed tools still need per-call access checks.

Revisit Code Mode

Make isolation easy to adopt.

PHP used the fewest tokens in our matched audit. A managed executor could keep that computation while removing the need for each Symfony app to operate gVisor.

Cloudflare’s Code Mode uses isolated Workers for JavaScript. That is a useful deployment model, not a drop-in PHP runtime. A PHP service would need verified isolation, per-call authorization, deadlines and cleanup, then fresh cost and latency comparisons.

02

Approve tools and set a policy

Symfony AI provides the tool schemas. The policy checks the caller and arguments on every invocation, including every call in a JSON submission. Tool descriptions never grant access.

code_mode:
    mode: catalog
    ai_toolbox: app.toolbox
    ai_tools: ['publication_read']
    ai_authorization: Adoption\ReadPolicy
    identity_provider: Adoption\LocalReader

Example configuration; use service IDs and tool names from your app. Read the complete working configuration ↗

    The trust boundary
    Useful access.
    Explicit limits.
    The host owns identity, tool permissions and budgets in both paths. JSON avoids running generated programs; it still invokes application code.
    01 / BOTH PATHSAuthorize every call
    Approved providers, schema validation and application access checks. Search results and tool descriptions never grant permissions.
    02 / JSONLiteral calls only
    No PHP, expressions, loops or result references. Existing handlers run under a supervised Unix worker. Calls stop on first failure; completed calls are not rolled back.
    03 / SANDBOXED PHPgVisor is required
    No unsafe local executor or ordinary-container fallback. The guest has no network, host mounts, credentials or Docker socket.
    04 / BOTH PATHSBounded work
    Host-owned call, time, memory and output budgets. Each proof records its actual limits; the PHP and JSON submission budgets differ.
    Authorization limits access; it cannot establish user intent for every otherwise permitted action. The live injection test demonstrates that distinction. These development proofs are not an independent security audit or a production-hosting certification.
